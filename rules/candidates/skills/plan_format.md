# 方案门面规范（pfb §8.1#1；2026-09-27 <角色>）

> 适用范围：team
> 版本：2026-10-06

**适用**：一切 `.kimi/plans/*.md`（新建与改准都算）。
**为什么有这份规范**（本批真实代价）：批 1–6 期间，用户因**方案名读不出问题、待拍板项散在多处**，
**两轮**专门回来逐条确认、会话往复多轮；同批还出现过"§7 两套编号（§7 与 §7 表 #2）"这种需要双方来回对齐的事。
⇒ 这三条是**把"确认延迟"从源头掐掉**的最低要求。

## 一、三条硬要求

### 1. 文件名带**症状词**
- 形如：`<问题域>_<一句话症状>_<YYYYMMDD-HHmm>_[状态].md`（**英文**，状态 ∈ `Pending|Doing|Done`）。
- **症状**＝"**谁**在**什么场景**看到**什么错**"，或"要实现**什么**"。
- 正例：`report_sharing_second_viewer_leak_20260927-0001_[Pending].md`（第二买家白看）、
  `font_scan_surface_log_text_hits_font_20260927-1235_[Pending].md`（一条日志词顶红门禁）。
- **反例**：`report_ownership_20260927-0001_[Pending].md` —— "报告归属"**读不出问题是什么**（本批用户原话）。

### 2. `§0` 固定为「**一页纸**」，且放在正文最前（在"现状核查"之前）
必须含三块，**顺序固定**：
1. **症状一句话**（谁／什么场景／什么错；或要实现什么）。写不出这一句 ⇒ 方案还没想清，别往下写。
2. **待用户拍板**（表格，**每行一个决定**）：`问题` ／ `推荐项（含代价）` ／ `备选（含代价）`。
   —— **不许把待拍板项埋在 §8/§10 里**（本批就是散在三处）；**每项必带代价/影响**。
3. **不做清单**（明确写出这次不做什么，防范围蔓延）。

### 3. **编号只一套**
- 只用 `§n`（`§1`、`§2`…）或其子节（`§2.1`）；**禁止**"§7 表 #2"这类**第二套编号**并存。
- 引用别处时写**全名**（文件名 ＋ §号），不要只写"§7"（本批因此出现过指代不清）。

## 二、它在流程里的位置（`AGENTS.md` §2 的细读）

```
点子 → 可行性评估 → 澄清提问 → 方案（本规范）→ 评审（用户指定人，原文写文末「## 评审」）
     → 撰写人逐条回应（采纳／不采纳＋理由，评审原文不动）→ 用户确认
     → 拆任务（每条带可复现验收；**任务记录走工具** `send`／`tick`／`done`，不再写 `pending.md`）→ 执行 → 独立复核 → 完成/归档
```

## 三、提交前自检（5 条，逐条打勾）

- [ ] 文件名里**有症状词**，且**看得出问题是什么**
- [ ] `§0` 一页纸**在最前**，含 症状一句话／待拍板（**带代价**）／不做清单
- [ ] **待拍板项一条也没埋在正文里**（grep「待用户拍板」只应命中 §0）
- [ ] **编号只有一套**（无"表 #N"式并列编号）
- [ ] `## 评审` 节存在，且写清"**请勿修改上方正文**"
- [ ] **送审前手跑一次** `python .kimi/tools/plan_facts_check.py`（引用文件／验收目标自检；该检查已退出 pytest 门禁，降为写方案人手跑）

## 四、本规范自己的用例（dogfooding）

- **正例**：`.kimi/plans/font_coverage_static_set_20260927-1235_[Pending].md`（名字直白）＋ 本规范逐条；
- **反例（留作教材）**：`report_ownership_20260927-0001`（已归档 Done）—— 名字含糊、待拍板散在 §4／§8.x／§10、出现过两套编号。
- **回检口径**（pfb §8.1#1 的验收）：拿上面那条反例按本规范逐条过 ⇒ **应被指出 ≥2 处不合规**（"名字"与"待拍板分散"）。
