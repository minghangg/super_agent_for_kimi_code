# 验证成本阶梯（L0–L3）· 抽象规则

> 适用范围：**所有项目**（本文件只讲「怎么选层」，不列任何项目命令）
> 一句话：**默认从最便宜的一层开始；每上一层，都要说出为什么非上不可。**

## 1. 四层

| 层 | 验什么 | 典型手段 | 量级 |
|---|---|---|---|
| **L0 静态** | 语法、结构、配置解析、产物与源一致 | 语法检查、JSON 解析、`grep -n` 断言、最小 harness 量尺寸 | 秒 |
| **L1 单元／契约** | 逻辑、接口、文案 | 定向单测（按文件／关键词），必要时该项目的快速门禁 | 数十秒 |
| **L2 浏览器／真机 smoke** | 真实渲染、交互、console | 真浏览器打开页面、点击、读 console | 分钟＋独占机器 |
| **L3 全量＋发版** | 能不能发版 | 全量门禁＋截图＋生产侧 `curl`／真机 | 十分钟＋生产风险 |

## 2. 按改动面选起始层（派单与复核都照这张表写）

| 改动面（看 diff 就能判） | 起始层 | 明确不许 |
|---|---|---|
| CSS 选择器／类名／文案／HTML 属性，无逻辑改动 | **L0** | 不许跑仓库级 smoke／多页浏览器套件 |
| 前端或后端逻辑（渲染、请求、状态、分支） | L0 → **L1** | 不许直接上浏览器全量 |
| API／契约／存储／数据形状 | **L1** | 不许拿人工点页面代替 |
| 门禁脚本／测试夹具本身 | **L1**（该脚本自身跑一次） | 不许只做语法检查 |
| 发版／部署 | **L3** | — |

## 3. L2／L3 准入（三条缺一不可）

1. 下层（L0／L1）已绿，且自测与独立复核完成；
2. 确实要上线，或必须看真实渲染才能判断；
3. **用户明确点头。**

AI **不得**自行跑 L2／L3。任务书里要写清「为什么非跑不可」，获批才跑；没写＝不许跑。跑 L3 不自动带浏览器许可。

## 4. 排序看代价，不看秒数

- 上层贵在**机器占用与易碎度**，不只看耗时：需要独占浏览器、会顶掉别人的测试、假红要复跑。
- 谁的机器跑哪层、哪些用例不由该机负责，见各项目机器档案；贴数字**必须带主机标签**。

## 5. 记录

- 验收写「**跑了哪层 ＋ 实测数字 ＋ 主机标签**」，不写「测试通过」。
- 一次改动**最多一个** L2 页面（除非另行获批）。
- 门禁日志与被测树绑档：文件名含被测 SHA 前 7 位，首行写 `HEAD=<sha>`。

## 6. 反例（真实发生过）

- 只改 2 行 CSS 类名，却跑 12 套无关页面的浏览器 smoke（≈13 分钟）⇒ 违规；正确做法是 4 条 `grep` ＋ 一个最小 harness 量尺寸。
- 用「上层跑绿了」代替「下层已跑」⇒ 违规：顺序是从下往上，不是从上往下补理由。

## 7. 项目命令去哪找

各项目把自己的 L0–L3 **具体命令**写在项目自己的规则里（例：`rules/<项目>/skill/verify_ladder.md`）。本文件不复制命令，避免耦合。
