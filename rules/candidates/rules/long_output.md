# 长输出处理（省 token · 硬要求）

> 适用范围：team
> 版本：2026-10-23
> 来源：用户 2026-10-23 裁定（headroom 调研结论 A：**只借鉴思路，不装第三方**）。调研见 `.kimi/report/headroom_survey_20261023.md`。
> 上位口径：根 `AGENTS.md` §8 索引；本文件是**细则**。

## 一、为什么要这条

实测（95 个会话，<项目> 最大的 6 个，`usage.record` 汇总）：**97.2% 的 token 是 cache-read（历史重发）**，新输入只占 2.8%；
其中 **tool result 约占新增输入的 22%**，且 **14% 的大结果吃掉了 60% 的字符量**。
⇒ 省钱的关键不是「装压缩器」，而是**别把大块文本一次塞进上下文**。

## 二、规则（8 条）

1. **先落文件**：预期输出 **> 200 行 或 > 10 KB** 的命令，一律重定向到文件再读摘要：
   - 正式日志落 `.kimi/logs/<name>_<YYYYMMDD-HHmm>.md`（本项目 `.kimi/logs/` 是唯一落点，见 `logs/README.md`）；
   - 一次性的临时输出落 `/tmp`（<机器1>）或 `%TEMP%`（<机器2>），用完即弃。
2. **只回摘要**：进上下文的只保留 —— **退出码**、**关键计数**（如 `80/80 passed`）、**错误行 + traceback 前 15 行**、产物路径。总长 **≤ 20 行**。
3. **定点取细节**：需要中间某段时用 `grep -n` / `sed -n 'a,bp'` / `tail -50`，**不整份重读**。
4. **测试输出**：只取 `== N/M passed ==`、`[FAIL]` 行、traceback 前 15 行；逐条 PASS 明细只有在**判据要求逐条**时才贴。
5. **构建 / 服务日志**：`grep -inE "error|fail|traceback|exception" | head -30`，必要时再 `tail -50`。
6. **报告与复核**：引用日志写「**路径:行号 ＋ 摘要**」，不贴原文；原文留在文件里，谁要谁去读。
7. **例外（必须原文）**：门禁判据要求的**退出码、逐条计数、哈希、关键字段值**原样保留 —— 这些是「真绿 vs 假绿」的分界线，不许摘要化。
8. **判据**：同一份日志在一次会话里**整份读入 ≤ 1 次**；第二次只允许 `grep`/`sed` 定点取。

## 三、反面做法（明确禁止）

- 先把大文件整份 `Read` 进来、再调「压缩工具」压 —— **先读后压等于没省**。
- 把 `git log` / `pytest` / `docker logs` / `npm build` 的完整输出直接贴进上下文。
- 在答复或报告里整段复制日志（应给路径 + 行号）。
- 为省 token 把**失败用例名**或 **traceback 关键帧**压掉 —— 那是判据，压了就是假绿。

## 四、与既有文件的关系

- `AGENTS.md` §7（答复格式）已要求「能用链接的就不复制内容」；本文件把它扩到**命令输出与工具结果**，并给出**阈值与落点**。
- 与 `.kimi/logs/README.md` 一致：正式日志落 `.kimi/logs/`，后缀 `.md`，入 git。
