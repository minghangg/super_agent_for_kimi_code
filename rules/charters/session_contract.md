# Session Contract（会话三契约 · 用户 2026-11-10 定）

> 本文件由 `tools/from_<项目>/dispatch_session/dispatch.py` 在**新建会话时**注入：
> 新会话的第一条消息＝「Only read 本文件 → Reply with exactly: ping」。适用对象：一次性
> worker（wk-*）、QA（qa-*）、PM 及一切经 dispatch 建立的会话。**只改本文件即可全链生效。**

## 1. 思考用英文

思考过程**一律英文，不写中文草稿再翻译**。遵守 **ASD-STE100**（简化技术英语）：

- 短句：一句一个主意。
- 一词一义。
- 主动语态。
- 避免缩略与歧义。
- **一句只给一个指令；每个指令句只含一个动作。**

输出时才译成用户语言。

## 2. 输出精准

- **一句一个意思；一句 ≤30 字，超了就拆。**
- 删空话：「我将开始…」「需要我继续吗？」「如有问题随时问」——一律不写。
- 删模糊词：「可能／大概／似乎／应该吧／差不多／有点」——一律不写。
- 只写事实、路径、数字、下一步。写「17 行」不写「一些行」；写「3 分钟」不写「一会儿」。
- **判据：每句都能指出主语＋动作＋对象；指不出来的句子删掉。**

## 3. 写码前检查顺序

按序执行，**遇到第一个可行方案立即使用，不要继续向下**：

1. 是否必要（YAGNI）
2. 代码库内复用
3. 标准库
4. 原生特性
5. 现有依赖
6. 极简实现
7. 手写代码

把「选了哪一级、为什么」一句话写进交付。


## 4. 新增能力必须接上生产路径（用户 2026-11-17 令）

**safkc 仓每新增一项能力，同一单内必须让它被生产路径调用。** 只写出代码、没人调用，不算交付。

「被生产路径调用」的定义：有真实入口（章程里的命令、工具的默认分支、引擎的每轮流程）在正常运行时走到它。**写文档、写测试、写函数都不算。**

**三个必查动作，缺一不可**：

1. **查调用方**：`grep` 出全部该能力的调用点。**有呼叫点就必须跳到它，不能是空壳。**
   - 两种情况都算「没接上」：①**没有任何调用方**（死代码）；②**有调用方，但生产路径走不到它**——参数没传、默认值绕开、条件永不成立。第二种更危险，因为它看起来像接上了。
2. **查手册冲突**：新能力若与现有章程、规则、手册的写法相反，**同一单内改掉旧写法**。两条相反的规矩并存，执行者必然照错的那条走。
3. **查旧路径**：新能力取代的旧路径要显式处置——删除、标注停用、或写明「并存到何时」。**沉默并存＝两条真源。**

**完工关单前，这三项逐项给出证据**（命令＋输出），写进交付。

**反例（2026-11-17 实测，注意它属于第二种）**：`super_agent/issue_cli.py` 早已实现 `--session-key` 选项，有人传它就追加 `<!-- session: … -->`。**问题不是没人调用这个工具**——全仓 23 处 `comment` 调用都在调它。问题是**那 23 处没有一处传 `--session-key`**，所以 `compose_body` 那个分支在生产中从未执行。结果 `_pm_verified` 恒为 False，release 铃自 #87 起一次没响过，四条 PM verdict 全被判 unverified。**能力写好了三天，等于不存在。**

**判据**：交付里必须能指出「**哪一行、在什么条件下**」会执行到它。只指出「谁 import 了它／谁调了这个工具」不够——要指出**那条分支的运行条件**。

## 5. 等待用事件，不用倒计时（用户 2026-11-18 令）

**一件事最多一个后台任务；要盯就盯一个永久循环，不盯一串倒计时。**

- **禁止**为同一件事连续创建 2 个及以上后台任务去读秒。典型错法：一串 `sleep 30`／`sleep 60`／`sleep 90` 排着等同一件事。今天实测出现过**同一件事建了 16 个一样的倒计时任务**。
- **为什么**：`sleep` 结束只说明「时间到了」，不说明「事情变了」。睡醒看不到变化就再睡一次，越等越多。
- **正确做法二选一**：
  1. **等事件通知**（首选）：`run_in_background=true` 跑那条真正的长命令，完成自动通知，不需要额外等待任务。
  2. **一个永久循环**：确需周期性查看的，只建**一个**，间隔 **N > 60 秒**，每轮自判「变了没有」，没变就结束本轮、**不续建**。
- **三条判据**：①同时存活的后台任务里指向同一件事的 ≤ 1 个；②等待类任务间隔必须 > 60 秒；③任务描述写清「等什么」，「等待」不是描述。
- **为什么 60 秒**：被等的事情（会话跑完、文件落盘、issue 出新评论）不会在几秒内变；需要「立刻知道」的场合走事件通知，不走轮询。

**与「>15 秒命令一律后台」不冲突**：那条管**跑一条长命令**，本条管**反复观察同一件事**。

## 6. 只用自己的身份发评论（用户 2026-11-18 令）

**每个人发评论，`--role` 必须是自己。** 不许用别人的角色前缀代替自己，也不许替别人发。

```bash

python -m super_agent.issue_cli comment --role <你自己> --project <项目> --issue <n> \

  --do <动作> --notify <提醒谁> --session-key <你的键名> --body-file <文件>

```



| 你的角色 | `--role` 取值 | 五段式首段写什么 |

|---|---|---|

| supervisor | `<本机 supervisor 角色名>` | 你的会话键名 |

| PM | `pm` | 你的会话键名（`pm-<项目>-<8位hex>`） |

| worker | `worker` | 你的会话键名（`wk-<任务>-<日期>`） |

| QA | `qa` | 你的会话键名（`qa-<项目>-ISS-<n>`） |

| scout／steward／auditor／reviewer／analyst | 同名 | 你的会话键名 |



**首行由工具拼装**：给了 `--do` 就拼五段式（§7），没给才退回旧式裸前缀。**新评论一律给 `--do`**——旧式只为 3000+ 条历史评论保留可解析性，不是给你用的。


**三条禁令**：

1. **禁止冒用他人身份**。supervisor 不许用 `[PM]`，PM 不许用 supervisor 的前缀，任何人不许用别的角色的 `--role`。
2. **禁止代发**。别人写的东西，让他自己发。§4「长命助手有评论权」之后，代发已无正当理由。
3. **`--role` 只有一个合法值：你自己**。工具里出现「`--role pm` 但操作者是别人」这类写法，一律视为冒用。

**为什么**（2026-11-18 实测）：

- **作者过滤形同虚设**：`engine.py:562-564` 按 GitHub `author` login 过滤，但**所有角色共用一个 token**，`author` 永远是同一个值 ⇒ **冒用不会被引擎挡住**，只能靠纪律。
- **冒用会制造假告警**：supervisor 用 `[PM]` 开头发裁决 ⇒ 引擎按 PM verdict 解析 ⇒ 无 `<!-- verdict: -->` 标记 ⇒ 判 `unreadable` ⇒ 落 `pm.unverified` + `needs_person` 假告警，且与真实投递重复。当晚报出 6 次 `pm verdict 'unreadable'` 即此类。
- **代发会破坏归属**：首行变成 `[PM] [代发:…]`，署名与作者不符，收单哨按前缀路由时会投错人。

**唯一例外**：`bind --role pm` 里的 `--role pm` 是**权限声明**（谁能登记会话归属），不是发评论署名，不属本条范围。

**判据**：`grep -n "comment --role" <你的章程>` 命中的 `--role` 值必须全等于你自己的角色名。

## 7. 评论标题五段式（用户 2026-11-19 令，2026-11-20 落地）

**首行标题必须写成五段**，取代旧的「只看 `[WK:<名>]` 标记」：

```
[who]-[do]-[notify]-[project]-[cid]
```

| 段 | 含义 | 取值 |
|---|---|---|
| `who` | 谁发的 | **你的会话键名**（`state/sessions.json` 里那一把），不是角色标记 |
| `do` | 干什么 | 下面 12 个动作之一 |
| `notify` | 要提醒谁 | 会话键名／`No Notify`／`All Active`／逗号分隔 |
| `project` | 所属项目 | `gh_projects.json` 的**短键**（`superagent`，不是 `super_agent_for_kimi_code`） |
| `cid` | 可选：回引上一条评论 | 纯数字 |

### 12 个合法动作（不在表内的**不计数、不通知**）

```
完工  收口  退回  裁决  告警  派单  接单
交接要求  交接完成  交接就绪  已归档  调试
```

### 三条硬判据

1. **`who` 必须是会话键名**。写 `[SC]`／`[PM]` 这类**裸角色标记不算交付**——它不携带名字，会造出匹配不上任何 assignment 的交付（`assignment.unmatched`）。
2. **`[调试]` 与 `[已归档]` 不通知任何人**。调试探针就是为这个存在的：**不要为了让探针被看见而假装成 `[完工]`**。
3. **`No Notify` 不影响计数**。配额管的是「收单哨会不会发提醒」，不是评论本身。

### 为什么改

旧口径「首行有 `[WK:<名>]` 就算交付」把 92 字节的探针和 5848 字节的真交付**同等计数**。后果实测过：探针吃满当日配额，真交付被熔断停发。

**结构表达意图，不靠字数猜。**

### 命令

```bash
python -m super_agent.issue_cli comment --role <你自己> --project <项目> --issue <n> \
  --do <动作> --notify <提醒谁> --session-key <你的键名> --body-file <文件>
```

`--do`／`--notify`／`--session-key` 三者由工具拼成首行；`--cid` 可选。
工具会校验 `--project` 是否在登记表内，错则列出全部可选短键。

### 三种带结论的评论：动作决定语义

| 你要表达 | 动作 | 还须带什么 |
|---|---|---|
| QA 复核结论 | `退回`（判不通过）／`完工`（判通过） | 首行末尾 `<!-- fix_needed: true\|false -->` |
| PM 裁决 | `裁决` | 首行末尾 `<!-- verdict: ready\|blocked\|working delivery: <cid> -->` ＋ issue 坐标 `#<n>`；**首段必须是 `pm-*` 或 `supervisor-*`** |
| 交付 | `完工` | 首段是你的会话键名 |

**其余动作（`接单`／`派单`／`交接要求`／`交接完成`／`交接就绪`／`告警`／`收口`／`已归档`／`调试`）不承载结论**——引擎不会把它们读成通过或裁决。

**旧式前缀仍有效**：`[PM] 可关单 #<n> <!-- verdict: ... -->`、`[QA] 结论：通过 <!-- fix_needed: false -->`、`[WK:<名>]` 都还能解析，因为 GitHub 上已有 3000+ 条历史评论是这个形状。**但新评论一律用五段式**——两套并存只为兼容，不是给你选的。

## 8. 新建会话＝两条命令（用户 2026-11-20 定）

**谁建会话谁负责 warmup。** 建会话时**不带** `--no-activate`，让工具自动跑 warmup；任务作为第二条命令发。

```bash
# 第一遍：建会话，自动 warmup（读本契约 + 读角色章程 + 告知你的键名）
python -m super_agent.dispatch_cli --cwd <工作台> --name <新键> --detach \
  --timeout 300 --task ""

# 第二遍：发真正的任务
python -m super_agent.dispatch_cli --session <新sid> --detach --no-activate \
  --timeout 300 --task "<任务>"
```

| 遍 | 判据 |
|---|---|
| 1 | wire 出现 `Read done.`，首条消息含 `session_contract.md` 与角色章程路径 |
| 2 | 出现任务的实际输出 |

**为什么不能合成一条**：warmup 占掉一轮，`--timeout` 预算被它吃掉，主任务就报 `round did not start within 120s`（此时 warmup 其实成功了）。

**`--no-activate` 只用于复用会话**（`--session`，本身就不跑 warmup，加它只是省掉多余等待）。**用它建会话 = 新会话没读过契约与章程**，是「派单成功但对方什么都不会」的静默形态。

**换血/轮换**另有一套七步流程，见 `rotation.md` §6.1。
