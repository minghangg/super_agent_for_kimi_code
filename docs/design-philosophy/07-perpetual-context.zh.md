# 07 · 永续上下文

## 执行摘要

整个行业在往「更大的上下文窗口」上跑。本文认为，这场竞赛瞄错了问题。

上下文窗口不是一个因为太小而不断溢出的容器。它是一个**因为装了不该装的东西**而不断溢出的容器。把它做大，只是推迟溢出，同时让每一轮都更贵 —— 因为窗口里的每一个 token，每一轮都要被重读一遍。

这个论点分五层：

1. **supervisor 的上下文应该是永续的。** 一个人和它顶层 agent 的工作关系，应该能持续好几个月。它不该被周期性销毁重建，也不该被项目细节填满。
2. **项目记忆属于 supervisor 之外。** 它活在记录里 —— Issue 里、文档里、产物库里。supervisor 持有的是**指针和判断**，不是**内容**。
3. **所以正确的架构是蚁群，不是更大的脑子。** 蚁后不知道食物在哪。蚁群找到它、记住它，而蚁后继续做只有它能做的那件事：决定。
4. **于是轮换变得又便宜又安全。** 会话换血时，只有极少量的全局事实跟着走。其余按需从记录里重读。失忆不再是风险，因为记忆从来就不在会话里。
5. **这个形状可以分形组合。** 一个 supervisor 带它的团队，对外呈现的契约和一个 worker 完全相同 —— **团队本身就是一个模块**。把模块挂在「supervisor 的 supervisor」下面，就构成更大的工程组织，而每个节点的上下文依然很小。「这只能用于小项目」这个反驳，答案是多加一层，不是换个更大的窗口。

这是整个系列里杠杆最高的一条主张，也是最容易被误读的一条。它没说上下文不重要。它说的是：**上下文太重要了，不能拿去装那些本来有更好去处的东西。**

## 1. 错误的诊断

### 1.1 为什么「更大的窗口」是直觉答案

症状是真的，而且很容易复现：一个工作了很久的 agent，开始犯一小时前不会犯的错。它忘了早先说过的一个约束。它把已经定下来的事重新讨论一遍。它把两个相似的东西搞混。

直觉诊断是「它没地方了」。直觉修法是「给它更多地方」。厂商在窗口大小上竞争，因为这个症状是普遍的，而这个修法是看得懂的。

但仔细看症状到底是什么。**agent 没有丢掉信息 —— 信息还在窗口里。它丢掉的是「判断窗口里哪一部分现在重要」的能力。** 更大的窗口修不了这个。它让这件事更糟：更多无关材料争夺同一份注意力，而且每一轮都要付费重读全部。

### 1.2 真正的诊断：污染，不是容量

把一个长期运行的会话的上下文拆开看：

```text
用户的意图与当前优先级                 ← 必须留
常设授权与硬边界                       ← 必须留
当前未决的问题，以及各自谁负责         ← 必须留
项目 A：文件路径、函数名、schema       ← 属于项目 A 的记录
项目 B：三周前的一次讨论               ← 属于项目 B 的记录
项目 C：某条需求的确切措辞             ← 属于项目 C 的记录
过去十二次工具调用的原文               ← 哪儿都不属于
```

前三行很小。剩下的没有边界，而且**随着 supervisor 接触的每一个项目增长**。这才是真正的机制：**supervisor 的上下文不是太小，是被当成了档案柜。**

把档案柜塞进 supervisor 的脑袋里，同时贵在三处：

- **每轮都费 token**，因为每轮都要重读。
- **费判断力**，因为信噪比下降，模型得花容量去决定该忽略什么。
- **费连续性**，因为窗口一满就必须换血 —— 而换血会把顶部那三样小东西，连同底下那些没有边界的东西一起销毁。

第三项成本没人做预算，而它正是「换血让人害怕」的原因。

### 1.3 更大的窗口到底买到了什么

假设窗口翻倍。会发生什么？

- supervisor 能撑两倍时间才换血。好。
- 每一轮现在最多要携带两倍的上下文。坏，而且这是**反复发生的成本**，不是一次性的。
- 污染问题没变，只是被推迟。
- 真到换血那天，丢掉的上下文更多，所以恢复包必须更大，所以恢复更贵。

**更大的窗口，把「频繁的小问题」换成了「罕见的大问题」。** 这不显然是改善。这是失败形状的改变，而对一段长期关系来说，这是错误的形状：你要的是失败**频繁、小、便宜**，不是罕见、大、灾难性。

## 2. 永续上下文

### 2.1 「永续」的确切含义

不是「永不压缩」。压缩是生活的现实，假装不是，设计就会变脆。

**永续的意思是：身份、意图、授权能穿过压缩；其余一切都可重建。**

一个永续上下文有三个性质：

1. **它装的东西是稳定的。** supervisor 上下文里的条目集合不随项目数增长。它随**未决事项**增长，而未决事项受人的注意力限制。
2. **它丢掉的东西是可重建的。** 压缩之后，supervisor 能通过对记录提一个精确的问题，重建它需要的任何项目细节 —— 而不是请人重新解释一遍。
3. **它对自己不知道什么是诚实的。** 一个已经把项目细节外包出去的 supervisor，应该说「我没有这个，我去查」，而不是用陈旧碎片拼一个听上去合理的猜测。

第 3 条最难，也最重要。**外包记忆只有在 agent 愿意承认缺口时才成立。** 一个半记得的 agent 比一个干净地忘掉的 agent 更糟，因为它会给出自信的错误答案，而且没人知道该去核。

### 2.2 压缩恢复包

一个会话被压缩时，必须带过去的东西少到可以枚举：

| 必须存活 | 为什么 |
|---|---|
| **用户是谁、想达成什么** | 无法从任何记录重建；它是所有记录的前提 |
| **当前授权与硬边界** | 从历史里重建又慢又易错，而搞错了很贵 |
| **未决事项，以及各自谁负责** | 这才是真正的工作队列；丢了就是丢了线头 |
| **记录在哪** | 指针，不是内容。够它问出对的问题就行。 |
| **别处没写下来的常设约定** | 写下来的就不用在这儿了 |

而必须**明确不带**的：

- 任何具体项目的文件路径与函数名。
- 过去工具结果的正文。
- 已解决讨论的原文。
- 任何「因为最近提到过」才被放进来的细节。

判断标准只有一个问题：**如果这条丢了，agent 一次查询能不能找回来？** 能，它就不该进包。包是给那些查不到的东西的 —— 因为它们除了在那段对话里，从没被写下来过。

最后这句才是真正的设计约束。**凡是重要的，要么写下来，要么进包。没有第三条路**，而失败模式就是假装有第三条路。

### 2.3 为什么这让换血变安全

换血现在吓人，是因为它对最有价值的状态做了一次有损操作。在永续上下文下，换血变成：

```text
换血
  → 加载那个小包（身份、意图、授权、未决事项、指针）
  → 对每个未决事项，向记录提一个精确的问题
  → 继续
```

成本与**未决事项的数量**成正比，与历史的长度无关。一个有 200 个已关 Issue、2 个未关的项目，恢复起来和一个有 5 个 Issue、2 个未关的项目一样便宜。**这才是让长期工作成为可能的性质。**

它也改变了换血的**用途**。它不再是应急程序（「窗口用完了」），而变成常规程序（「这个任务做完了，会话剩下的上下文是开销」）。上一篇的 35% 规则之所以安全，正是因为这个性质 —— **当没有任何有价值的东西只活在那里时，你才扔得起一个会话。**

## 3. 蚁群

### 3.1 谨慎地陈述这个比喻

蚁群能运作，是因为没有一只蚂蚁知道整个蚁群的计划。蚁后不知道食物在哪。觅食蚁找到它、回来，信息通过局部互动传播。蚁群的记忆是分布的：在信息素轨迹里、在巢的结构里、在蚂蚁的身体里。

这个映射不是装饰。每一部分都对应一个真实的设计决定：

| 蚁群 | 团队 |
|---|---|
| 蚁后：繁殖与群体级决定 | **supervisor**：意图、授权、仲裁 |
| 觅食蚁：找到并搬运食物 | **worker**：各执行一个交付物 |
| 信息素轨迹：持久、会衰减、可寻址 | **记录**：Issue、文档、产物 |
| 局部互动规则，没有中央计划 | **引擎**：确定性流转 |
| 巢的结构：稳定、缓慢变化 | **角色与边界**：谁可以做什么 |

这个比喻说对的地方：**蚁后的无知是特性，不是缺陷。** 如果蚁后必须知道食物在哪，蚁群就无法扩展到超过一个脑子能装下的规模。蚁后的上下文之所以小，**正是因为**蚁群被组织成它可以小。

这个比喻说错的地方，也是我们不该照抄的地方：蚂蚁没有「为什么」的概念。我们的觅食蚁有，而记录必须保存意图，不只是位置。信息素轨迹说「食物在这边」；Issue 说「我们要这个，因为这个原因，受这些约束」。**记录必须比轨迹更丰富，也因此维护起来更贵。**

### 3.2 进化论的论据

蚁群不是为好看挑来的比喻。它是**生物进化的产物**，而这正是它适合资源受限的 agent 团队的原因。

先看一只蚂蚁究竟是什么：

- 一个约二十五万神经元的神经系统 —— 比人类少四个数量级。
- 对蚁群的目标没有任何表征。没有地图，没有计划。
- 对没遇到过的问题没有推理能力。
- 寿命以周计，所以它无法积累长期经验。

按工程师的任何一种衡量标准，单只蚂蚁都是一个非常糟糕的 agent：上下文极小、没有推理、没有值得一提的记忆。然而这样一群蚂蚁**能跨越地形完成集体迁徙、能把觅食力量分配到多个食物源、能建造温控结构、能在大部分成员被毁后恢复**。这些事，人类需要一张地图、一份计划和一个会才能尝试。

答案在于：进化优化的不是蚂蚁，**它优化的是蚁群**。智慧不在节点里，而在节点之间的互动规则里，以及它们留在环境中的持久痕迹里。单只蚂蚁的失败很便宜 —— 它死了，蚁群只是少了千分之一只觅食蚁。**而蚁群的记忆，比其中每一个个体的死亡都活得久。**

这就是本文对 agent 团队的主张，用生物学的语言说一遍：

| 蚁群 | Agent 团队 |
|---|---|
| 单只蚂蚁：无上下文、无推理、脑子极小 | **worker / QA**：一个交付物，无长期记忆 |
| 蚁群：解决任何蚂蚁都解决不了的问题 | **团队**：解决任何单个 agent 都解决不了的问题 |
| 信息素轨迹：比留下它的蚂蚁活得更久 | **记录**：比写下它的会话活得更久 |
| 进化选择的是群体适应度 | **设计应当选择团队适应度** |

这条可迁移的主张令人不适，但它承重：**如果进化发现「一群很笨的节点」胜过「少数很聪明的节点」，那么把每个节点变聪明就不显然是正确的投资方向。** 更大的上下文窗口，正是「把每只蚂蚁变聪明」的一次尝试。蚁群给出的答案是：把**互动**做好，把**痕迹**做持久。

这也解释了为什么这套设计不要求每个节点都有强推理模型。一个读到精确任务书、改掉被点名的文件、跑完被点名的验收命令的 worker，不需要对项目做推理 —— **推理已经在任务书里发生过一次，并被保存在记录里**。智慧是被摊到整个架构上的，而不是压缩进每一个会话。

### 3.3 分布具体买到了什么

三样一个大的单上下文不可能有的性质：

**隔离。** 两个项目不可能污染彼此的决定，如果它们在不同的会话里。一个大的单上下文没有这种保证 —— 一切都与一切相邻。

**并行。** 独立的工作可以推进，而不必在一个上下文上串行。一个单上下文必须一次处理一件事。

**轮换粒度。** 一个项目可以被换血，而不碰其他项目。单上下文是全有或全无。

以及一样它**丢掉**的性质，必须说清楚：**分布会丢掉「一切都在一处」带来的意外交叉授粉。** 一个单上下文有时会注意到两个项目有同一个问题。分布式团队只有在有人去问的时候才会注意到。缓解手段是 supervisor 的角色 —— 它是唯一能观察到跨项目模式的地方，**正是因为它持有所有项目的指针、而不持有任何一个的内容。**

### 3.4 supervisor 作为唯一的共享节点

这是让蚁群成立的结构性主张：**supervisor 是唯一看见所有项目的节点，而它只以指针的形式看见它们。**

这个组合，才是让跨项目判断成为可能、同时不让上下文膨胀的原因。supervisor 能问「哪几个项目卡在同一个依赖上？」，因为它持有所有项目的未决事项列表。它没法回答「项目 B 的 schema 长什么样？」除非去查，而它也不该试着回答。

纪律是：**supervisor 的价值在于它能问的问题，不在于它持有的答案。** 一个持有答案的 agent 是缓存。一个持有问题的 agent 是编排者。缓存会过期，问题不会变钝。

### 3.5 分形组合：团队即模块

蚁群论证有一个容易漏掉的推论，而它正是对「这套东西只能小规模用」这一质疑的回答。

**一个 supervisor 带着它的团队，本身就是一个模块。**

看模块是什么：一条边界加一份契约。给它输入，拿到输出，调用方不需要知道里面发生了什么。worker 满足这一点 —— 给任务书，拿回一个交付。**但一整支团队也满足这一点** —— 给一个目标，拿回一个交付。**两者的接口完全相同。** 差别只在成本、延迟，以及调用方要隔多久才需要再看一眼。

这个同一性，才让这套架构**分形** —— 每一层自相似：

```text
第 2 层   supervisor 的 supervisor      持有 M 个指向第 1 层模块的指针
             │
      ┌──────┼──────┐
      ▼      ▼      ▼
第 1 层  supervisor  supervisor  supervisor   每一个都是模块，契约相同
             │             │            │
      ┌──────┼─────┐       │            │
      ▼      ▼     ▼       ▼            ▼
第 0 层  worker  worker  worker  worker  worker  worker   基本情况：内部
                                                          不再有监督
```

每一层规则都一样，而这一点才是承重的：**第 *k* 层的节点持有意图、授权、未决事项，和 M 个指针 —— 从不持有内容。** 它的上下文是 O(M)，不是 O(它下面的工作量)。M 受「一个节点能有效跟踪多少件事」限制，而那是人的注意力常数，不是项目数常数。

所以「这只能成立因为你的项目小」这个反驳，**误读了被扩展的是什么**。被扩展的不是节点，**是层数**。加一百个项目，不会让顶层 supervisor 的上下文大一百倍 —— 它只是多了一层，而每一层的每个节点依然很小。

三个值得说清的推论。

**可替换性。** 因为团队和 worker 呈现同一份契约，一个团队可以占据原先 worker 的位置，反过来也行。你可以从一个 worker 起步，活变大了换成一整支团队，而上面那一层完全察觉不到。**这就是「模块」的含义**，也是为什么项目长大时不需要重写设计 —— 槽位没变，只是填进去的东西变了。

**统一的失败语义。** 每一层，失败都意味着同一件事：模块没交付，或者交付了上一层不接受的东西。升级永远是往上一层。**没有「这是个大项目」的特例，也没有第二套规模规则。**

**有界，但不免费。** 组合不是免费的。每一层都增加一次意图的重新表述，而每一次重新表述都会损失保真度 —— 「为什么」会随着下沉而衰减。每一层都增加延迟。每一层都多一个可能引入错误前提的地方。分形组合让规模**成为可能**，让代价**可预测**；它没有让代价变便宜。一个五层结构，顶层节点上下文再小，也仍然有五次把目标译错的机会。

把基本情况与递推说明白：

- **基本情况：** 一个 worker，一份任务书，一个交付。内部没有监督。
- **递推：** 用 N 个模块，外面套一个 supervisor，它的上下文装它们的契约与未决事项。结果仍是一个模块。
- **所以：** 任意层数，每一层都满足同一性质。

而这之所以不只是「加个层级」：层级只是一个形状。这里的主张是**接口跨层不变**，所以同一条纪律 —— 薄角色、指针而非内容、记录而非会话 —— 在每一层都原样适用。一个每一层接口都不同的层级结构，只是一棵更高的树，顶部那层的上下文问题一点没变。分形的那个，让每个节点都保持小 —— 这是完全不同的一件事。

## 4. 判据：什么进，什么出

四个问题，用于任何一条候选信息。

### 4.1 它是否只属于一个项目？

是，它就属于那个项目的记录，supervisor 最多持一个指针。检验方法：**另一个项目的 PM 会需要这个吗？** 不会，它就是项目细节，而 supervisor 上下文里的项目细节就是污染。

### 4.2 它能否一次查询就找回来？

能，它就不该进包。包是给那些查不到的：意图、授权、未决事项，以及别处不存在的约定。

推论是一条维护规则：**当你发现自己要把一条能写下来的东西放进包里时，去把它写下来。** 包是例外，每一次往里加东西，都应该稍微有点不舒服。

### 4.3 它下个月还成立吗？

常设事实（用户是谁、边界是什么）属于包。瞬时事实（刚才在改哪个文件、上一个报错是什么）不属于 —— 它们属于带时间戳的记录，或者哪儿都不属于。

一个有用的启发式：**如果这条事实自带一个日期，它是记录条目，不是包条目。**

### 4.4 它是一个决定，还是一个细节？

决定属于拥有它的人，并作为未决项被跟踪。细节属于记录。失效模式是**把决定记成了细节** —— 「我们决定用方案 B」埋在一段注释里 —— 这会变得不可恢复，因为没人知道那曾是一个决定。

缓解手段是一条格式规则：**决定单独成条，带理由和被考虑过的备选。** 一个没有理由的决定不可恢复；一个带理由的决定，在情况变化时可以正确地被重新讨论。

### 4.5 一个具体的回忆包

上面的判据容易点头，难以落地。下面是我们实际用的形状 —— 小到几分钟能写完，具体到会被证伪。

```text
─── 身份 ─────────────────────────────────────────
用户是谁，一两句话。
他最终想达成什么。

─── 常设规则 ─────────────────────────────────────
硬边界（绝不做 X）。
常设授权（Y 已预先批准）。
别处没写下来的约定。

─── 未决事项 ─────────────────────────────────────
逐条：问题是什么、谁负责、卡在哪。
（如果超过个位数，说明 supervisor 手里攥着
 本该派出去的活。）

─── 地图 ─────────────────────────────────────────
有哪些项目。
每个项目：记录在哪、当前在做什么。
不写任何内容。

─── 近期历史，压缩 ───────────────────────────────
自上一个包以来变了什么，几行。
够避免重新讨论已定的事。
```

关于这个形状，有三点值得注意：

**它刻意是无聊的。** 没有任何地方可以放一个「有意思的细节」。这就是设计：**包里的有意思的细节，就是此后每一轮都要被重读的细节。**

**「未决事项」是唯一会长大的部分。** 身份和常设规则近乎恒定。地图随项目缓慢增长。未决事项随人的注意力增长，而那是真正的约束。**如果包在变大，诊断是未决的事太多 —— 不是包需要新格式。**

**地图是承重的。** 包里其他东西原则上都能重建；地图不能，因为没有它，agent 不知道该去查什么。当人们为了省地方而修剪包时，**地图是最后一个该被拿掉的。**

一个有用的失败测试：**把包交给一个新会话，给它一个未决事项，看它能不能行动，而不问一个包本该回答的问题。** 如果它得问「这是哪个项目？」，地图不完整。如果它得问「那个文件现在什么状态？」，包工作正常 —— 那是一次查询，而查询正是记录存在的理由。

## 5. 反方观点

这么强的主张，值得把反对意见公平地摆出来。

### 5.1 「查询慢，所以放在上下文里更快」

真的，而且这是最强的一条。一次查询要一个来回；事实已经在上下文里，那一轮就不用额外花钱。

回应是：**查询的成本有界，污染的成本无界。** 一次查询一个来回。一个被污染的上下文，此后每一轮都要付一份，永远，而且它以一种很难归因的方式降低判断力。在一段长期关系里，累计成本占主导。

但这条反对意见有真实的内核：**对短任务，上下文胜过查询。** 一个读完文件就改的一次性 worker，当然该把文件留在上下文里。**永续上下文这个论证适用于长命角色，不适用于每一个会话。** 把它套到短工身上就是过度工程。

### 5.2 「不在上下文里，模型就想不起来」

也是真的，而且这是这条反对意见最锋利的版本。外包记忆要求 agent **知道去问**。一个不知道某个项目存在的 agent，永远不会去查它。

回应是：这是**设计责任，不是记忆属性**。supervisor 的上下文里必须有一个「存在什么」的索引 —— 项目列表、未决事项列表 —— 尽管它不含任何内容。**索引很小、有界，而它正是让查询成为可能的东西。**

所以包不只是「身份、意图、授权」。它还包括「**一张地图，标明其余一切住在哪**」。没有地图，外包失败；有地图，外包成立。

### 5.3 「这能成立只是因为你的项目小」

在单层上部分成立，**但作为普遍反驳不成立** —— 见 §3.5。单个节点的上下文是 O(M)，M 是它监督的模块数，而 M 是人的注意力常数。扩到一百个项目不会撑大顶层节点；它只是加了一层，每一层的每个节点依然很小。

仍然成立的部分：**一个** supervisor 装不下一百个模块。这是「该加一层」的理由，不是「架构失效」的理由。地图多一层，不是大一个数量级。

诚实的残余代价是每层一次的保真度损失，§3.5 已说明 —— 组合有界，但不免费。

### 5.4 「你只是在描述一个多了几步的数据库」

有点道理。外包记忆加一个小索引加精确查询，结构上就是一个前面站着 LLM 的数据库。

回应是：**这正是重点，而且这是个好架构。** 有趣的问题不是它像不像数据库，而是边界画在哪。我们的答案是：**边界画在语义判断上。** 任何需要读和判断的留在模型那边；任何属于查询或流转的，交给记录或引擎。**一个前面站着模型的数据库，是对「模型做判断、存储做存储」这种系统完全合理的描述。**

我们拒绝的是相反的安排：**一个同时也是存储的模型。** 那就是大上下文，也正是本文反对的安排。

## 6. 这解决不了什么

- **它不能把一份烂记录变好。** 外包记忆的好坏上限就是记录的好坏。如果 Issue 写得含糊，查询返回的就是含糊，而 supervisor 会自信地照着含糊行动。
- **它不免除换血。** 它让换血便宜，不是让它不必。会话仍然有窗口。
- **它不让 supervisor 全知。** 它让 supervisor **对自己的无知诚实**，这是另一件事，而且更有用。
- **它不消除交叉授粉的损失。** 分布式团队确实会漏掉一个单上下文本来会抓到的东西。supervisor 部分补偿了，不是完全补偿。
- **它没有解决模型问题。** 某个模型在「知道什么时候该去查」上够不够好，是一个实证问题，而它是这套设计承重的那一根。
- **它不使组合变免费。** 每加一层，就重新表述一次意图，就损失一点保真度。分形结构能扩展，也会可预测地退化 —— 但一个五层结构有五次把目标译错的机会，上下文再小也修不了这个。

## 7. 一段话说完

行业对上下文限制的回答是更大的窗口。我们的回答是一个更小的、永远不需要重建的上下文。差别不是程度上的：**更大的窗口保持同一套架构、让每一轮更贵；永续上下文改变架构装什么、让每一轮更便宜。**

一个 supervisor 应该知道用户的意图、当前的授权、未决的事项，以及其余一切住在哪 —— 别的都不该知道。其余一切属于记录：需要的时候能找到，不需要的时候不花一分钱。

而且因为**团队对外的契约与一个 worker 相同**，这个形状会重复：在 supervisor 之上再放一个 supervisor，组织就长大了，而每个节点依然很小。

**蚁群找到食物。蚁后做决定。** 正是这个分工，让两者都能工作非常久 —— 也让「蚁群的蚁群」同样成立。
