# 04 · 面向人的 Reporter 状态中心

> 系列：设计哲学（design-philosophy）｜[01 核心架构](01-core-architecture.zh.md) ｜ [02 需求分析员](02-requirements-analyst.zh.md) ｜ [03 Agent 间通信](03-agent-communication.zh.md) ｜ 04 面向人的 Reporter ｜ [05 产物回收站](05-artifact-recycle-bin.zh.md)｜ [06 Token 经济学](06-token-economics.zh.md) ｜ [07 永续上下文](07-perpetual-context.zh.md)
> 版本：2026-11-07
> 定位：为用户提供只读、准确、按需下钻的状态视图，代替询问多个 Agent 或阅读评论流水。
> 性质：设计报告，不授权修改规则、开发代码、开启 Web 服务或改变角色权限。

## 一、目标

用户想确认状态时，不再需要：

- 打开多个 Agent 会话；
- 询问 supervisor；
- 阅读 Issue 评论流水；
- 等 LLM 临时总结。

改为打开一个 Reporter 页面：

> **现在有哪些任务、进行到哪里、哪些需要我处理、是否存在风险。**

## 二、角色定位

Reporter 是**只读状态展示器**，不是新的管理 Agent。

它应该：

- 从运行索引、Issue 和事件里读取状态；
- 生成面向人的汇总；
- 提供项目、任务和证据的下钻；
- 优先显示需要用户处理的事项；
- 标明数据更新时间和来源。

它不应该：

- 派单；
- 催办；
- 修改任务状态；
- 代替 supervisor 裁决；
- 为了生成状态而调用高成本 LLM；
- 持有生产或密钥权限。

## 三、信息架构

### 1. 首页：只回答四个问题

```text
① 需要我处理什么？
② 当前有哪些任务在推进？
③ 哪些任务阻塞或异常？
④ 系统本身是否健康？
```

推荐布局：

```text
需要用户处理
├─ 需求待回答：2
├─ 方案待裁决：1
└─ 发布待验收：1

项目概览
├─ 项目 A：执行中 2 ｜ 等待 QA 1
├─ 项目 B：无异常
└─ 项目 C：冷却等待 1

系统状态
├─ 事件总线：正常
├─ 执行引擎：正常
└─ GitHub 同步：3 分钟前
```

正常项目尽量压缩，不用大量「运行正常」消息占屏。

### 2. 项目页

每个项目显示：

- 当前目标；
- 活动 Issue；
- 当前阶段；
- 负责人；
- 正在等待什么；
- 最近有效进展；
- 下一步；
- 风险与阻塞。

不展示 worker 的全部聊天过程。

### 3. Issue 详情页

采用「摘要＋时间线＋证据引用」：

```text
目标
当前状态
最新决定
最新交付
QA 结论
待用户事项
相关 Issue/评论链接
```

需要细节时再打开原文，不默认展开全部评论。

### 4. 需求澄清页

与 Analyst 的补充设计衔接：

- 待回答的问题；
- 推荐选项；
- 问题影响；
- 集中提交；
- 提交后返回状态页。

Reporter 可以呈现该页面，但答案写入仍走独立、受限的需求接口。

## 四、技术实现

首版建议纯程序生成：

```text
index.json
＋ requirements/index.json
＋ GitHub Issue 当前状态
＋ 事件总线/引擎 health
        ↓
只读状态投影
        ↓
本地 HTML Reporter
```

不需要数据库。

可以采用：

- 单个本地 Web 服务；
- 普通 HTTP GET 页面；
- 定时或事件触发刷新；
- 数据缓存只保存短状态；
- 页面提供原文链接。

WSS 不是首版必要条件。需要实时更新时，可复用事件总线能力，或先使用页面定时刷新。

## 五、状态必须诚实

每个状态都应区分：

- 正在执行；
- 等待 worker 交付；
- 等待 QA；
- 等待 supervisor；
- 等待用户；
- 等待模型冷却；
- 已完成但未发布；
- 已关闭；
- 状态未知或数据过期。

禁止把：

- `busy=false` 显示为「已完成」；
- HTTP 请求成功显示为「业务成功」；
- 旧缓存显示为「实时正常」；
- 未验证交付显示为「验收通过」。

页面每项状态至少带：

```text
来源 ＋ 更新时间 ＋ 是否过期 ＋ 详情链接
```

## 六、与 supervisor 的关系

Reporter 上线后：

- 用户主动问「现在怎么样」时，可以直接看 Reporter；
- supervisor 不再为状态查询读大量项目资料；
- supervisor 仍负责回答「为什么这样决定」；
- Reporter 负责回答「现在是什么状态」。

遇到状态不一致时，Reporter 只展示冲突和来源，不自行裁定谁正确。

## 七、权限与安全

- 默认只监听 `127.0.0.1`。
- 只读页面与答案提交接口分离。
- 页面不显示 token、密钥、隐私数据或无关日志。
- 不从用户输入生成可执行命令。
- 详情访问遵守项目范围。
- 如需公网或局域网访问，必须另行设计鉴权并获明确批准。

## 八、与系列其他组件的关系

```text
Agent 间简化通信
        ↓
产生结构化状态、结果引用和事件
        ↓
Reporter 将这些数据投影成人类可读页面
```

两者共享数据契约，但职责不同：

- Agent 间通信减少机器之间的沟通成本；
- Reporter 减少人的状态获取成本。

Reporter 不反向成为 Agent 调度入口。Analyst 的问题与答案可以由它展示，但需求修改权限仍归独立的受限接口。

## 九、实施顺序

1. 先提供静态/本地只读状态页。
2. 接入活动 Issue、Analyst 需求和系统健康。
3. 增加项目与 Issue 下钻。
4. 增加「需要用户处理」的集中入口。
5. 验证状态准确性后再考虑实时刷新。
6. 用「用户是否还需要询问 Agent 查状态」检验效果。

## 十、验收指标

- 用户查看全局状态所需的点击次数和等待时间；
- 需要用户处理的事项是否能在一屏内找到；
- 状态与 Issue/引擎真源的一致率；
- 过期状态是否被明确标识；
- 用户为查状态而询问 supervisor 的次数；
- 页面是否泄露凭据、隐私或无关项目细节。
